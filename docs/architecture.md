# 实现原理

WhiskerWind 不修改 QQ 客户端，也不实现 QQ 的私有网络协议。它把官方 Linux QQ（Electron 应用）运行在容器内的虚拟桌面中，借助 Linux 桌面的两套标准接口与之交互：

- **桌面通知（D-Bus `org.freedesktop.Notifications`）**：获知「哪个会话来了新消息」；
- **无障碍接口（AT-SPI）**：读取界面内容、定位并操作控件。

在此基础上，协议端将读取到的消息整理为统一的内部事件，再由各协议适配器转换为 OneBot v11、Satori 或 automatic 协议对外提供。

## 1. 容器组成

```
┌──────────────────────────── 容器 ────────────────────────────┐
│  Xtigervnc (:99)   openbox   D-Bus 会话总线   AT-SPI 总线       │
│                                                              │
│  QQ (Electron, --force-renderer-accessibility)               │
│     │ 桌面通知（D-Bus）          │ 界面树（AT-SPI）              │
│     ▼                           ▼                             │
│  qqcache serve (Python) ── SQLite（消息、身份映射、通知记录）     │
│     │ 内部事件                                                 │
│     ├─ OneBot v11 适配器  :5700  HTTP / 正向 WS / 反向 WS / POST │
│     ├─ Satori 适配器      :5500                                │
│     └─ automatic 适配器   :5600                                │
│                                                              │
│  WebUI BFF (Node.js) :3000 ── 经 OneBot HTTP/WS 访问 serve      │
└──────────────────────────────────────────────────────────────┘
```

| 组件 | 作用 |
|---|---|
| Xtigervnc | X 服务器兼 VNC 服务，为 QQ 提供显示环境，也用于远程查看界面 |
| openbox | 窗口管理器，负责窗口焦点与层级 |
| D-Bus 会话总线 | QQ 通过它发送桌面通知；协议端在其上注册通知服务 |
| AT-SPI 总线 | 无障碍接口。QQ 以 `--force-renderer-accessibility` 启动，Chromium 会把页面 DOM 的类名和 id 以属性形式暴露出来 |
| qqcache serve | 协议端主体：接收通知、读取与发送消息、解析身份、驱动协议适配器 |
| WebUI BFF | 管理面板后端，持有 access_token，前端只与 BFF 通信 |

容器入口脚本（`docker/entrypoint.sh`）作为 PID 1 运行，依次启动上述组件，并持续守护 QQ、serve 与 BFF：任一进程退出后约 10 秒内重新拉起；QQ 主进程存活但界面树消失（渲染进程崩溃）时，也会将其结束并重启。

## 2. 接收消息

### 2.1 通知驱动

协议端在会话总线上注册 `org.freedesktop.Notifications`，替代桌面环境的通知服务。QQ 每收到一条非当前会话的消息，就会调用 `Notify`，其中摘要为会话名，正文为「发送者：内容预览」。

通知只用作触发信号，消息内容以界面为准：

1. 协议端取得 GUI 锁，对该通知发出 `ActionInvoked` 信号。QQ 据此按内部会话 id 切换到对应会话，同名会话不会混淆。若会话未切换，则改为点击侧栏中可见的会话项。
2. 通过 AT-SPI 读取消息列表。每条消息对应一个 `ml-item` 节点，节点 id 即 QQ 的原生消息 id（msg_id）；从中解析发送者、方向、时间、正文、图片与文件等内容。
3. 按 msg_id 去重并写入 SQLite，再按时间顺序生成内部事件。

### 2.2 弥补通知盲区

QQ 在以下情况下不发送通知，协议端分别处理：

| 情况 | 处理方式 |
|---|---|
| 当前打开的会话 | 每 2 秒轮询一次当前会话的消息列表（`--poll-interval`） |
| QQ 窗口持有键盘焦点时，其他会话的消息 | 每次界面操作结束后，将焦点交给一个不可见的占位窗口 |
| 协议端重启、焦点被占用等期间到达的消息 | 盲区结束后读取会话列表（只读，不点击），对比未读数、最后消息时间和预览，补处理遗漏的会话 |
| 通知处理失败（例如 QQ 渲染进程崩溃、界面正在重建） | 分别在 65 秒、3 分钟、10 分钟后完整读取一次会话列表，对仍有未读的会话补处理；读不到会话列表时每 30 秒重试 |
| 设置为免打扰或「接收不提醒」的会话 | 不处理。这类会话本身不产生通知，补处理也只针对曾经产生过通知的会话，以免打开大量未读的群 |

### 2.3 发送者身份

通知和消息列表中只有显示名（群名片或昵称），没有 QQ 号。协议端按以下方式确定真实 QQ 号：

1. 点击消息旁的头像，打开资料卡，读取其中的「QQ 号」字段；
2. 若头像已不在可见区域，则从群成员列表打开该成员的资料；
3. 仍无法确定时，分配一个稳定的合成 id（≥ 900000000000，由群号与显示名计算得出），之后解析成功再通过专门的事件通知下游合并身份。

同一群内出现同名成员时，协议端不按名字归因，而是对每条消息单独解析，避免把消息记到错误的人名下。成员解析在每批消息中有时间预算，超出预算的成员留待下一批处理，不会长时间占用界面。

群号与私聊对象的 QQ 号同样来自会话的资料卡，并缓存在本地。

## 3. 发送消息

所有界面操作共用一把 GUI 锁，按顺序执行。一次发送的流程如下：

1. **限速检查**：同一会话 10 秒内最多 3 条、60 秒内最多 12 条，全局 60 秒内最多 20 条；30 秒内向同一会话发送相同内容会被拒绝。超限时直接返回错误，不会排队延后发送。
2. **打开目标会话**：已缓存的会话从侧栏打开；未缓存的通过「综合搜索」按 QQ 号查找。
3. **核验目标**：会话名必须与缓存一致，且打开会话资料卡读出的 QQ 号必须等于目标号码。任一项不满足即放弃发送。
4. **填写输入框**：输入框是 ProseMirror 编辑器，不支持通过无障碍接口写入文字，因此文字和图片经剪贴板粘贴（Ctrl+V）；@成员通过输入 `@` 后在候选面板中选择插入；引用回复通过消息右键菜单的「引用」实现。
5. **发送前复核**：粘贴完成后确认会话没有被切换，再点击「发送」。
6. **确认回显**：在消息列表中找到刚发出的消息，取得其 msg_id 作为返回值。

步骤 1–3 中的失败保证没有产生任何副作用，调用方可以安全重试；步骤 4 之后的失败会在错误信息中说明可能已部分执行。

撤回、禁言、戳一戳同样通过右键菜单完成，并在操作前进行同样的目标核验。

## 4. 登录与状态

- **登录态**：通过界面树判断 QQ 处于已登录、等待扫码还是未运行状态。
- **二维码**：截取屏幕上的二维码区域返回给 WebUI；二维码过期时自动点击刷新。
- **被挤下线**：自动关闭下线提示框，记录提示内容并推送系统通知事件，WebUI 据此弹窗提示。协议端不会自动重新登录。
- **设备标识**：`machine-id` 保存在数据卷中，重建容器后 QQ 不会将其识别为新设备。

## 5. 协议适配

协议端内部只有一种事件模型（消息、成员身份更新、登录态变化、系统通知、心跳），各协议适配器负责转换：

- **OneBot v11**：消息 id 映射为 int32，消息内容输出为 CQ 码或消息段数组。详见 [webui-api.md](webui-api.md)。
- **Satori**：群同时作为 guild 和 channel，私聊为 `private:<QQ号>` 频道，消息 id 直接使用 QQ 原生 msg_id。
- **automatic**：本项目定义的协议，见 [automatic-protocol.md](automatic-protocol.md)。

各协议与其标准规范之间的功能差异见 [compatibility.md](compatibility.md)。

## 6. 性能特征

| 项目 | 典型值 |
|---|---|
| 收到消息到推送事件 | 1–3 秒；首次出现的群成员需额外解析，约 3–6 秒 |
| 发送一条消息 | 1–5 秒（含目标核验） |
| 并发 | 所有界面操作串行执行 |

这些数值取决于界面响应速度，在会话数量多、置顶会话多或主机负载高时会变长。
