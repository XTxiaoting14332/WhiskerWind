# 已知问题与排查

本页列出已知的功能限制，并按现象说明排查方法。排查时通常需要查看三处信息：WebUI 的「服务日志」页、「状态与设置」页中的屏幕截图，以及 `docker logs`。日志与接口的位置见[运行与维护](/guide/operations)。

## 功能限制

- **发送串行执行**：所有界面操作共用同一个 QQ 窗口，排队依次执行。发送一条消息约需 1–5 秒，调用超时建议不少于 60 秒。
- **免打扰会话不产生通知**：设置为免打扰或「接收不提醒」的会话，QQ 不发送通知。「只提醒 @」的群只会产生 @ 本账号的通知。
- **历史范围有限**：`get_msg_history`、群成员列表等只包含服务启动后经过的消息，以及发过言的成员。
- **消息段有限**：支持文本、@、图片与引用。表情、语音、视频降级为占位文本。合并转发与卡片消息可以接收，但内容为摘要文本，且不支持发送。
- **版本绑定**：界面结构随 QQ 版本变化。镜像固定使用经过验证的 QQ 3.2.33。

## 收到消息后没有响应

建议按以下顺序排查。

1. 调用 `get_login_state`，确认返回 `logged_in`。
2. 查看服务日志，搜索会话名称或消息内容。日志中出现「处理通知」，表示协议端已开始处理该会话；出现「emit N 条」，表示已推送 N 条消息。
3. 检查会话的提醒设置。设为免打扰、「接收不提醒」或「只提醒 @」的会话不产生通知。协议端只轮询当前打开的会话，因此这类会话的消息需要在会话打开时才能被读取。

以下原因也可能导致消息延迟或遗漏。

- **界面正在重建**。QQ 的渲染进程偶尔会崩溃，重建期间（通常为一到几分钟）无法读取和打开会话，这段时间到达的消息会处理失败。协议端会在 65 秒、3 分钟和 10 分钟后各做一次未读巡检，补处理仍有未读消息的会话。日志中的「未读巡检」与「处理失败后」即对应此过程。若 QQ 主进程退出，入口脚本会在十几秒内重新启动 QQ。
- **同一会话的通知被合并**。同一会话在 15 秒内的多条通知只触发一次处理，之后再补处理一次。消息不会丢失，但会有延迟。
- **界面正忙**。发送消息、解析群成员身份、批量补处理等操作占用界面，新消息需要排队，可能延迟数秒到数十秒。
- **QQ 窗口持有焦点**。QQ 持有键盘焦点时，其他会话不发送通知。协议端会在每次界面操作结束后，把焦点交还给桌面。
- **有人在 VNC 中操作 QQ**。手动点击会打乱协议端正在进行的操作。VNC 仅建议用于查看界面。
- **账号已掉线**。见下文。

## 账号掉线或被挤下线

在其他设备上登录同一账号、长时间离线或触发风控时，QQ 会被下线。协议端会关闭下线提示框，并在 WebUI 中弹出提醒，但不会自动重新登录。需要在 WebUI「状态与设置」页重新扫码。掉线期间收到的消息，会在重新登录后通过未读巡检补处理。

## 群成员的 user_id 先是较大的数字，之后发生了变化

协议端需要通过界面打开资料卡，才能得到群成员的真实 QQ 号。

- 默认情况下，群消息会在发送者的真实 QQ 号解析完成后再推送，因此 `user_id` 通常已经是真实 QQ 号。解析每位新成员约需 3–6 秒，每批消息的解析时间上限为 15 秒。
- 解析失败、超出时间上限，或已关闭「先解析后推送」（`set_resolve_first`）时，消息以合成 ID（≥ 900000000000）推送。之后解析成功，协议端会推送 `qqcache_member_resolved` 通知（Satori 为 `qqcache/member-resolved` 内部事件）。同一成员两次解析尝试之间至少间隔 2 分钟。
- 若机器人按 `user_id` 存储权限、积分等数据，应处理该通知以合并身份，或忽略合成 ID 的用户。

## 发送消息失败

| 现象 | 说明 | 处理方式 |
|---|---|---|
| retcode 1429 | 触发出站限速或重复内容拦截。同一会话 10 秒内最多 3 条、60 秒内最多 12 条；全局 60 秒内最多 20 条；30 秒内向同一会话发送相同内容会被拒绝 | 降低发送频率，或等待后重试。被拦截的请求不会发出，也不会排队延后发送 |
| retcode 1400，错误信息包含「身份验证失败」「发送目标被切换」「拒绝打开」「没有找到会话」「残留内容」「当前状态」或「不在无障碍树」 | 协议端在输入文字之前已中止，消息没有发出 | 可以直接重试。反复出现时，检查目标是否仍在好友或群列表中 |
| retcode 1400，其他错误信息 | 消息可能已经部分执行，例如内容已粘贴但未点击发送 | 重试前先在 QQ 中确认是否已经发出，以免重复发送 |
| 调用超时 | 发送需要 1–5 秒，排队时更久 | 将 HTTP 客户端或框架的超时时间设为不少于 60 秒 |

## 回复速度慢

发送一条消息通常需要 1–5 秒。首次出现的群成员还需要额外解析身份，约 3–6 秒。会话数量多、置顶会话多或主机负载高时，延迟会更明显。这是通过界面操作 QQ 的固有开销。

## 启动与连接问题

- **容器启动后立即退出**。`VNC_HOST` 被设为非回环地址，但未设置 `VNC_PASSWORD`。入口脚本会输出「会把桌面暴露到网络上，请同时设置 VNC_PASSWORD」并退出。
- **WebUI 显示「容器离线」**。WebUI 后端无法连接协议端。执行 `docker exec whiskerwind pgrep -fa "qqcache serve"` 确认协议端是否在运行，并查看 `/var/log/qqcache.log`。
- **修改环境变量后没有生效**。环境变量在容器创建时写入，需要重建容器。仅重启容器无法使新值生效。
- **反向 WebSocket 一直处于 connecting 状态**。参见[接入 Bot 框架](/guide/bot-frameworks)中的连接排查。

## 二维码与登录状态

- **状态为 `login_required`，但页面没有二维码**。协议端会尝试切换到二维码页面。若长时间没有出现，查看「状态与设置」页的截图，确认 QQ 停留在哪个界面。
- **`qr_expired` 为 `true`**。协议端会自动刷新二维码。
- **`/qr` 返回 404**。当前没有可取得的二维码，通常是因为已经登录。
- **状态为 `unknown`**。界面状态无法识别，可能处于切换过程中。稍后重试，或查看截图。

## 自检

协议端提供分阶段的链路自检接口，可以定位入站链路中断的环节。自检会切换到指定会话并读取其中的消息，执行期间协议端的其他界面操作会排队等待。

```bash
TOKEN=$(docker exec whiskerwind cat /var/lib/qqcache/access-token)
curl -s -X POST "http://127.0.0.1:5700/run_selftest?access_token=$TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"conv": "会话名称"}'
```

自检按顺序执行以下阶段。前一阶段失败时，后续阶段不再执行。

| 阶段 | 检查内容 |
|---|---|
| `atspi` | QQ 是否已接入无障碍树 |
| `login` | 登录状态是否为 `logged_in` |
| `notify_bus` | `org.freedesktop.Notifications` 是否由协议端持有 |
| `notify` | 探针通知能否经 D-Bus 送达并写入数据库 |
| `open` | 能否打开指定会话，并确认打开的会话名称 |
| `attribute` | 能否确定该会话对应的 QQ 号 |
| `emit` | 能否读取会话中的消息 |

响应中的 `ok` 表示是否全部通过，`failed_stage` 为断点所在的阶段。每次自检的报告都会追加到数据目录中的 `qqcache.sqlite3.selftest.jsonl`。
